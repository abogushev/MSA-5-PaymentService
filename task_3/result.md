#### Вариант №1: оркестратор в одном из существующих сервисов
Плюсы: 
    - нет дополнительного сервиса для обслуживания
    - меньше сетевых хопов
Минусы:
    - смешение доменной логики и процессов
    - связь релизов доменной логики и логики процессов
    - отдельная команда будет должна поддерживать и доменную логику и логику процессов
    - можно использовать только в рамках одного домена
    - масштабирование зависимо: нужно иметь ввиду и доменную и процессную часть

#### Вариант №2: оркестратор в отделньом сервисе
Плюсы:
    - сервис выполняет строго одну функцию, нет смешивания зон ответственности доменной логики и процессов
    - релиз логики процессов не затрагивает релиз доменной логики
    - сервисом может владеть отдельная команда
    - можно переиспользовать для разных процессов
    - прозрачность процесса выполнения
    - масштабирование не зависимо  
Минусы:
    - появляется ещё один сервис, который нужно поддерживать/деплоить/мониторить
    - больше сетевых хопов

Вывод:
    Выбираем отдельный сервис потому что:
        - в процессе участвуют несколько сервисов. Сложность бизнес-процесса
        - уже используется Camunda BPMN 
        - нет высокой требований к сетевым задержкам
        - проще масштабировать
        - можно поддерживать разными командами
        - легко и безопасно изменять и релизить процессную логику, не влияя на доменную
